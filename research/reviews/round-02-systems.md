## 可复现的重要错误

### P0：延长面板末年会改写先前年份

`annual_panel()` 先在整个 end 范围按论文 ID 排序并按 DOI 去重，再构造年度行。若后年记录 ID 更小，它会吞掉先年同 DOI 记录。

最小反例：两条单作者 A 的论文，`id=Z, year=2000, doi=same` 与 `id=A, year=2001, doi=same`。只计算截至 2000 年时，2000 行累计论文数为 1；加入后条并将 end 延长至 2001，2000 行变成 0。独立执行已确认。

这不一定表示真实数据已有多少错误，但它直接反驳当前历史行不受未来记录影响的保证。只测试“加入 end 之后的论文，end 不变”覆盖不到这个情况。

**验收**：建立明确重复版本策略，确保未来记录不能删除当时已经可见的记录；对相同 DOI 不同 ID/年份、相同 ID 不同内容、不同输入顺序分别测试。把整段面板的第 t 行与仅计算到 t 的结果逐字段对比，不能只比较最终 input hash。

### P0：查询完整性认证没有检查事件内容一致性和已知事件缺失

`Observation.reveal` 保存事件 ID 集合，重复 ID 静默跳过，只检查已知邻居包含关系。两例均被现实现接受：

```python
s = Observation(1, 2000)
s.reveal(1, [(10, 1990, [1, 2])])
s.reveal(2, [(10, 1995, [1, 2, 3])])
# 同 ID 的时间与作者集合冲突，被忽略；2 仍标成 complete。

s = Observation(1, 2000)
s.reveal(1, [(10, 1990, [1, 2]), (11, 1991, [1, 2])])
s.reveal(2, [(10, 1990, [1, 2])])
# 已知作者 2 的事件 11 缺失，仍标成 complete。
```

CN 区间在正确的完整查询模型下有合理数学依据，现有穷举验证也有价值。但输入契约被违反时依然发布 completed 状态，不适合作为线上采集的证书依据。冻结事件库的开发实验未必触发此错误，不能因此推翻其全部数值；生产有效性仍必须修复。

**验收**：事件 ID 对应不可变、规范化内容指纹；按作者记录已观察事件集合；验证响应覆盖所有已知关联事件，任何冲突均在状态修改前拒绝。再测重复查询、同响应重复事件、不同作者顺序、空响应、已知缺页，以及断点恢复后的一致性。

### P1：作者索引的断点恢复不完整

`TemporalCorpus` 依次写 `.indptr.npy`、`.events.npy`、`.first.npy`，启动时只用 indptr 存在与否决定是否重建。若进程在第一次写完后中断，下一次会跳过构建并加载不存在的另两个文件。已有文件也未和源 NPZ 的版本绑定校验。

**验收**：临时目录生成、逐文件校验、最后原子提交 manifest；加载检查三个文件及源数据哈希。注入每一步中断、截断文件、陈旧索引后，重启可重建而非手工删除。作者分块评测本身已有临时文件替换，这是可保留的正确机制。

### P1：锁文件没有覆盖默认启动与干净重跑

`run.sh` 仍安装 requirements.txt 的范围依赖，未使用 requirements.lock；锁文件生成注释又依赖 `/tmp/das-schloss-runtime-constraints.txt`。锁文件作为安装输入本身可用，但原生成命令不可凭仓库完整重现。

**验收**：默认运行路径采用明确的锁定策略与哈希校验；保存可再生成锁文件的约束源和解释器范围；在干净环境安装并重跑冻结真实子任务，记录依赖版本、数据哈希、逐例预测与最终统计的一致性。当前 45 项测试是在原环境运行，不能代替这一步。

## 实验与系统主张尚缺的证据

预算 40、n=128 的开发结果：DBLP 的 uncertainty 策略 CN micro Recall@10=0.05556，高于 ambiguity_cover 的 0.04321；MAG-History 的 ambiguity_cover、uniform_cover、random、observed_degree 同为 0.07692。ambiguity_cover 的历史 top10 认证率分别为 7.03% 和 3.13%。这些数值说明历史排名恢复、认证率与未来合作预测不是同一目标，不能挑某个指标后宣布总体获胜。

1. 现有 runner 明确拒绝非 development 阶段，这阻止把开发分数偷换成测试分数，是优点；同时意味着冻结选择后的验证/测试仍未实现。需要完整实现该路径并保留不可修改的选择 artifact，至少跨截止年/领域检验。
2. 完整作者查询的真实成本差异很大。40 个查询不等于固定 API 页数、下载量或计算量；必须同时报告/比较按返回事件或页数的预算。热点作者查询往往更昂贵，策略优势不能仅由更大的实际成本取得。
3. evaluator 提前构造 full_cn 会预热 query_cache；策略 elapsed 不宜直接称作线上端到端成本。应将查询、索引、评分、oracle 验证计时分开，并有冷缓存工作量测量。
4. 索引使用 mmap 是合理路线，但 query_cache 无上界，n128 的约 400 MB 不足以证明 n10000 的内存预算。测量目标数和预算增长曲线，再决定 LRU/分块；当前不能认定需要更大机器。
5. 在线用户界面接通了描述指标和排名，新的预算采集与证书仍是离线实验。若论文声称完整决策系统，需要在线工作流、错误恢复和实际结果审计；若研究贡献是离线方法，正文应如实限定，不能把两条路径拼成已经部署的自动决策。

## 下一轮的可验证完成条件

先修复上述两个 P0 与索引断点错误，并增加独立回归测试；完成干净环境复现。随后冻结开发选择，以相同成本比较基线，在预留年份/领域运行真实预测及证书覆盖评估，给出不确定性、个体/团队依赖处理和失败分母。再以实测规模曲线决定硬件取舍。只有工程与研究证据都成立，才有理由考虑 6 分以上；当前仍不支持停止改进。
